# MiMo-V2.6-Flash-RL on 8× R9700

`mimo-v26-flash` serves the original Xiaomi checkpoint and its original
scales. The target weights were not replaced by the Diffbot checkpoint. The
useful ideas from [Diffbot MiMo](https://huggingface.co/diffbot/MiMo-V2.6-Flash-RL-FP8KV-W4A8-2x-RTX-PRO-6000)
were ported to the existing ROCm/Triton path instead of copying its CUDA
SM120 kernels.

The development profile `dev/mimo-v26-flash-mopd` pins Xiaomi's independent
MOPD update at revision `2479e2d0029eca9a34cc7e7f55a121925f81908e`. Xiaomi
states that this checkpoint specifically mitigates repeated or highly similar
tool calls. Its architecture, 172,923,364,096-byte tensor payload and DFlash
artifact are compatible with the qualified R9700 runtime, but it remains a
candidate until the full checkpoint download and A/B gates finish.

## Production configuration

- 8× `gfx1201`, TP8, ROCm 10, eager scheduling, maximum context 1,048,576.
- `TRITON_ATTN_DIFFKV` with QK=192/V=128, split-KV multi-token verify and a
  one-program DFlash verification tile.
- gfx1201 prefill tile: `BLOCK_M=64`, four warps, two stages.
- DFlash K=7 using the 2.94 GB drafter shipped with the Xiaomi checkpoint.
- BF16 KV cache and automatic prefix caching, with retention checkpoints every
  1280 tokens. FP8 KV is deliberately disabled; see the rejected experiments.
- Native `R9700Mxfp4Experts` from libr9k for grouped MXFP4×FP8 MoE. Original
  packed weights and exponent scales remain unchanged (`R9K_FOLD=0`).
- The gfx1201 MoE prefill kernel keeps routed-row scales in LDS, uses a
  coalesced 16-byte staged BF16 epilogue and skips the redundant output
  zero-fill when expert parallelism is disabled. The decode kernel is
  unchanged.
- gfx1201-specific Triton W8A8 FP8 GEMM tables for the dense QKV, gate/up and
  down projections. Every selected BF16 result is bitwise-identical to the
  former default kernel on the tuning corpus; approximate-only winners were
  rejected before the model-level A/B test.
- Maximum two scheduled sequences. C2 gave the best aggregate/interactivity
  compromise; C4 did not improve aggregate output throughput.
- LiteLLM 1.103.0 serves the MiMo alias with the model's agentic sampling
  recipe (`temperature: 1.0`, `top_p: 0.95`, `repetition_penalty: 1.05`).
  Greedy sampling is rejected because it can lock a compacted agent session
  into a deterministic tool-call cycle. The adaptive gateway guard permits
  four unique parallel read-only or `Agent` calls, limits mutable calls to one,
  deduplicates repeats and cancels violating streams. This is a safety boundary
  for coding-agent commands, not a scheduler limit; the runtime remains C2.
- Image input remains enabled for up to eight images. Video and audio remain
  disabled.

The runtime log must contain all of the following before a measurement is
accepted:

```text
Using TRITON_ATTN_DIFFKV for attention.
Using R9700Mxfp4Experts
r9700: native FP8/MXFP4 MoE -> R9700Mxfp4Experts (libr9k grouped MXFP4xFP8)
Loaded DFlash mask embedding ...
GPU KV cache size: 1,107,745 tokens
```

## Controlled results

The cold tests use exact token counts, greedy generation, `ignore_eos`, 256
output tokens and the repository's vLLM Bench wrapper. Prefill is
client-observed rather than a kernel-only number.

| workload | configuration | TTFT | effective prefill | decode | E2E/output throughput | acceptance |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 32K C1 cold | baseline, no speculation | 9.660 s | 3,392 tok/s | 21.0 tok/s | 11.8 tok/s | — |
| 32K C1 cold | DFlash K3, tuned prefill | 9.107 s | 3,598 tok/s | 62.4 tok/s | 19.4 tok/s | 75.0% |
| 32K C1 cold | DFlash K7, tuned prefill | 8.726 s | 3,755 tok/s | 87.0 tok/s | 22.0 tok/s | 53.8% |
| 128K C1 cold | baseline, no speculation | 76.211 s | 1,720 tok/s | 21.0 tok/s | 2.9 tok/s | — |
| 128K C1 cold | DFlash K7, tuned prefill | 51.420 s | 2,549 tok/s | 90.9 tok/s | 4.7 tok/s | 54.3% aggregate sample |
| 32K C2 cold | production K7 | 14.734 s/session | 2,366 tok/s/session | 41.0 tok/s/session | 24.2 tok/s aggregate | 59.5% |
| 32K C4 cold | production kernel, C4 trial | 28.805 s/session | 1,384 tok/s/session | 16.2 tok/s/session | 22.2 tok/s aggregate | 54.8% |
| 32K C1 cold | production before dense W8A8 tuning | 8.756 s | 3,742 tok/s | 100.9 tok/s | 22.7 tok/s | 65.3% |
| 32K C1 cold | bitwise-safe dense W8A8 tuning | 8.647 s | 3,790 tok/s | 101.3 tok/s | 22.9 tok/s | 65.3% |
| 128K C1 cold | bitwise-safe dense W8A8 tuning | 51.444 s | 2,548 tok/s | 99.7 tok/s | 4.7 tok/s | 63.5% |
| 32K C1 cold | pre-MoE-prefill control | 8.692 s | 3,770 tok/s | 93.8 tok/s | 22.4 tok/s | 63.5% |
| 32K C1 cold | staged MoE prefill epilogue | 8.334 s | 3,932 tok/s | 99.9 tok/s | 23.5 tok/s | 63.5% |
| 128K C1 cold | pre-MoE-prefill control | 53.275 s | 2,460 tok/s | 100.4 tok/s | 4.6 tok/s | 66.7% |
| 128K C1 cold | staged MoE prefill epilogue | 50.452 s | 2,598 tok/s | 104.7 tok/s | 4.8 tok/s | 66.7% |

At 32K, DFlash K7 improved cold decode by about 314% and total output
throughput by about 87% over the no-speculation baseline. At 128K, cold TTFT
improved by about 33% and decode by about 334%.

The isolated r9700-stack MoE prefill backport improved cache-clean effective
prefill by 4.29% at 32K and 5.59% at 128K; TTFT fell by 4.12% and 5.30%,
respectively. Both pairs used the same random-token seed, zero warmups, one
request after a fresh runtime start and `--skip-ready-check`. Prefix-cache
counters reported zero hits. Decode changed slightly even though the patch
does not alter decode; those single-sample differences are treated as noise.

Automatic prefix caching was tested with the same 32K token-ID prompt twice.
TTFT changed from 8.733 s cold to 0.162 s warm, while the server counter
increased by exactly 32,736 cached tokens. A mixed hit/miss benchmark must not
be summarized using its arithmetic mean; its per-request samples are retained
in the artifacts.

Long-context tool calls passed with 32,089 and 130,393 actual prompt tokens.
Both returned `get_temperature({"city":"Warsaw"})`. Basic generation,
streaming, a two-turn tool loop, and PNG image input also passed through the
real API.

The tool-streaming regression originally reproduced malformed Bash arguments
with default model sampling: direct vLLM produced 6 invalid results in 50
requests. Deterministic sampling made that narrow test pass, but a compacted
long-running Claude Code session then exposed the more serious failure mode:
one completion repeated two identical Bash calls 154 times while DFlash
acceptance converged to 100%. Sampled decoding alone was not sufficient: a
second compacted completion cycled through four validation commands until it
hit the 32,000-token output limit. Every transcript block reported the same
320,723-token input and 32,000-token output usage, proving this was one model
completion rather than client retries.

The original rollback fence combined `parallel_tool_calls: false` with a
`</tool_call>` stop. It reduced an adversarial "repeat Bash forever" request
from 512/512 generated tokens to 72 tokens non-streaming and 110 tokens
streaming, but also serialized independent repository exploration.

Production now uses the adaptive LiteLLM guard in
`r9700/litellm_tool_guard.py`. It permits up to four unique read-only calls or
four unique `Agent` calls, keeps mutable and unknown tools to one call,
deduplicates canonical name/JSON-argument pairs, repairs duplicate IDs and
closes the upstream iterator on a limit violation. Tool data is bounded to
64 KiB and ten seconds; arguments are never logged. Live qualification passed
four parallel read-only calls through both OpenAI and native Anthropic
streaming, and suppressed the fifth call in streaming and non-streaming
responses. The former YAML fence remains the immediate rollback. Image
`count_tokens` also returned HTTP 200. Run the parser regression again with:

```bash
.venv/bin/python scripts/test-litellm-tool-streaming.py \
  --iterations 50
```

Patch `0006-fix-qwen3-streaming-final-parameter.patch` also hardens the MiMo
Qwen3 parser against a model response that closes `</function>` without first
closing the final `</parameter>`. The parser now treats the function boundary
as the unambiguous end of that parameter and emits the missing JSON suffix.
This prevents a streamed prefix such as `{"command":"...` from reaching the
client as permanently malformed JSON. Complete-call deduplication and upstream
cancellation belong to the LiteLLM guard rather than the parser.

Runtime allocation at `gpu_memory_utilization=0.96` leaves about 1.2 GB VRAM
outside the vLLM budget on each 32 GB card. The final C2 BF16 KV pool contains 1,107,745
logical tokens, enough for one native-limit request or several shorter
requests. A smaller utilization value was not restart-stable: one run had only
6.45 GiB usable KV for a 6.48 GiB requirement.

## TP8 exact P2P all-reduce

Production uses the r9700-stack exact N-rank P2P collective for contiguous
BF16/FP16/FP32 tensors up to 256 KiB. Messages up to 16 KiB use the one-shot
kernel, messages from 16 to 256 KiB use the two-shot reduce-scatter/all-gather
kernel, and larger or unsupported tensors fall through to RCCL. Eight-rank
correctness, repeated calls and HIP Graph replay passed before model testing.

The vLLM platform must resolve to `R9700Platform`; setting
`VLLM_TARGET_DEVICE=rocm` bypasses out-of-tree platform selection and silently
leaves the model on RCCL. The production profile therefore relies on the
r9700 platform plugin's ROCm detection. Startup is accepted only when every
rank logs `r9k 8-rank P2P all-reduce installed`.

Full-model C1 A/B, same MiMo weights, DFlash K7, sampling, cache policy and
three measured repetitions after one warmup:

| workload | backend | TTFT | observed prefill | decode | E2E |
| --- | --- | ---: | ---: | ---: | ---: |
| 128 in / 512 out | RCCL | 60.65 ms | 2,110.4 tok/s | 151.22 tok/s | 3.440 s |
| 128 in / 512 out | r9k AR8 | 60.74 ms | 2,107.3 tok/s | 165.96 tok/s | 3.140 s |
| 32K in / 256 out | RCCL | 8.540 s | 3,837.1 tok/s | 147.06 tok/s | 10.275 s |
| 32K in / 256 out | r9k AR8 | 8.061 s | 4,065.2 tok/s | 162.69 tok/s | 9.628 s |

AR8 improves decode by 9.75% on the short workload and 10.63% at 32K. Short
prefill is neutral (-0.15%); the measured 32K TTFT improvement is 5.61%.
The C2 safety run completed six requests at 162.88 tok/s per request and
315.87 aggregate output tok/s with Jain fairness 0.999997.

## Rejected experiments

| experiment | result | decision |
| --- | --- | --- |
| FP8 E4M3 KV, stock prefill tile | 32K TTFT 48.469 s, 676 tok/s prefill, 19.3 tok/s decode | rejected |
| FP8 E4M3 KV, `BLOCK_M=128` | 32K TTFT 22.864 s, 1,433 tok/s prefill | rejected |
| BF16 prefill `BLOCK_M=128` | 3,286 tok/s prefill | rejected |
| BF16 prefill `BLOCK_M=64` | 3,833 tok/s screening result | selected |
| DFlash K3 | higher acceptance but lower E2E speed than K7 | rejected |
| C4 scheduler | no aggregate gain over C2 and much worse per-session latency | rejected |
| unconstrained dense W8A8 tuning | 32K prefill 3,579 tok/s, decode 93.3 tok/s, acceptance 57.8% | rejected |
| prefill-only dense W8A8 tuning | 32K prefill 3,577 tok/s despite faster isolated GEMMs | rejected |

The checkpoint does not provide calibrated E4M3 KV scales. Scale 1.0 doubled
the nominal cache capacity but introduced casts/dequantization in the active
prefill path and regressed it heavily, so production keeps BF16 KV. The native
MoE path was already present and faster than importing Diffbot's NVIDIA Marlin
path; no weight conversion was performed.

The dense W8A8 FP8 GEMMs for `(N,K)=(1856,4096)`, `(4096,4096)` and
`(4096,2048)` now use measured R9700 tables. Isolated kernels improved by up
to 1.8× in the decode-relevant buckets, but their small share of total model
time limits the 32K end-to-end gain to about 1.3% prefill and 0.4% decode.
The remaining bottlenecks are the 47 native MXFP4 MoE layers, DiffKV attention
at long context, and TP8 synchronization rather than an untuned dense GEMM.

## Future nice-to-have: audio and video input

Keep video and audio disabled in the production profile until they are
qualified independently. The checkpoint already contains the vision tower,
audio encoder, speech embeddings and audio tokenizer, and the pinned vLLM
source implements image, video, audio and interleaved video-audio inputs.

- Video is the lower-risk next step: enable one video per prompt, use the
  existing OpenCV decoder, bound frame count/resolution, and validate a real
  API request plus VRAM, TTFT and DFlash acceptance. It shares the already
  loaded vision tower with image input.
- Audio input requires pinning the ROCm-matched `torchaudio` package in the
  recipe first. Validate 24 kHz WAV and compressed audio decoding, resampling,
  standalone audio-to-text and video-with-audio. Do not advertise audio output
  or TTS; the current serving path returns text.
- DFlash currently receives text-only draft inputs for multimodal requests;
  the target model still verifies the result, but acceptance and speed may be
  lower. Compare DFlash K7 against no speculation for both modalities.

Promotion criteria are successful cold/warm API tests, stable startup and VRAM
headroom, correct content understanding, no regression to text/image traffic,
and explicit limits in `runtime.multimodal.limit_per_prompt`. Until then keep
`video: 0` and `audio: 0`.

## Install, start and rollback

```bash
./run install --profile mimo-v26-flash --dry-run
./run install --profile mimo-v26-flash
./run launcher start mimo-v26-flash --ready-timeout 900
.venv/bin/python scripts/smoke-mimo-v26.py
```

Rollback to the measured no-speculation control without changing Git state:

```bash
./run launcher switch dev/mimo-v26-flash-baseline --ready-timeout 900
```

Return to production:

```bash
./run launcher switch mimo-v26-flash --ready-timeout 900
```
