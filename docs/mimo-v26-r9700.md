# MiMo-V2.6-Flash-RL on 8× R9700

The `mimo-v26-flash` profile is an isolated correctness-first TP8 deployment.
It preserves the official checkpoint's FP8/BF16 dense layers and native MXFP4
experts. A narrow r9700-stack adapter routes only the native MXFP4 MoE layers
to `libr9k`; Qwen profiles and their compressed-tensors path are unchanged.

The baseline uses Triton DiffKV attention, BF16 KV cache (`auto` for this BF16
model), native 1M context, one sequence, eager execution, and RCCL. Image input
is enabled for up to eight images per prompt through the TP8 vision encoder in
`weights` mode; video and audio are disabled. Speculation, prefix cache, CPU
offload, expert parallelism, and custom TP2 all-reduce remain disabled. MXFP4
exponent folding is disabled so the baseline preserves the checkpoint scales
exactly; it remains an opt-in optimization for a later accuracy and performance
comparison.

With the TP8 vision encoder loaded, the checkpoint's native 1048576-token limit
retains 121506 tokens of margin below the measured 1170082-token BF16 KV
capacity. The earlier 8K startup exposed only 190577 logical tokens because
hybrid global and sliding-window cache groups were padded inefficiently at that
short limit. Chunked prefill remains capped at 8192 tokens, so increasing the
total context does not create a single one-million-token scheduler batch.

## Checkpoint size and speculative heads

The main index contains `172923364096` bytes (161.05 GiB) across 64 model
shards plus `model_mtp.safetensors`: shard 0 is 13.4 GB, the remaining 63
expert shards are about 2.5 GB each, and the MTP file is 1.19 GB (1.11 GiB).
The MTP file contains three learned next-token prediction layers. MiMo does not
contain the host-resident int6 PLE/lookup module used by the Qwen Flash-Next
deployment. The architecture is a 309B-parameter MoE with about 15B parameters
active per token; packed MXFP4 expert storage is why the checkpoint is much
smaller than a BF16 representation of all parameters.

The repository also ships a separate 2.94 GB (2.73 GiB) five-layer DFlash
drafter under `dflash/`. It uses a block size of eight and is distinct from an
n-gram lookup. Neither MTP nor DFlash is enabled in this baseline; they must be
qualified after ordinary decode is correct, with acceptance and end-to-end
throughput measured separately.

The checkpoint also includes both audio paths: a 308M-parameter AudioTokenizer
encoder and a 127M-parameter audio patch encoder. Their local weights are
complete, but audio input remains disabled in this profile. Loading both would
consume roughly another 2.23 GiB per TP rank and would materially reduce the
full-context BF16 KV margin. Video is disabled for the same production scope;
the enabled multimodal path is image-only.

## Install and inspect

```bash
./run install --profile mimo-v26-flash --dry-run
./run install --profile mimo-v26-flash
./run launcher start mimo-v26-flash --dry-run
```

The last command prints the resolved environment and server command without
starting the service. The checkpoint must contain all 65 indexed weight files
and exactly `172923364096` bytes of weights before a real launch can pass model
validation.

## Launch and smoke test

```bash
./run launcher start mimo-v26-flash
.venv/bin/python scripts/smoke-mimo-v26.py
```

The launcher exposes the direct OpenAI endpoint at
`http://127.0.0.1:8000/v1` and the stable LiteLLM alias
`mimo-v2.6-flash` at `http://127.0.0.1:4000/v1`. The smoke script checks basic
generation, SSE streaming, a parsed tool call, and a second turn containing the
tool result.

After correctness is established, benchmark the unchanged baseline before
testing FP8 KV, longer context, compilation/graphs, prefix caching, EP, or a
compatible MiMo drafter. Those optimizations are intentionally absent from the
baseline so each can be reverted and measured independently.

## Validation state

Completed on eight R9700 cards with ROCm 10:

- all repository unit tests pass;
- the pinned runtime installs cleanly and its HIP modules target `gfx1201`;
- runtime imports report PyTorch `2.13.0+rocm10.0.0` and the ROCm platform;
- the `fp8` registry selects `R9kFp8Config`, and native MXFP4 expert weights
  are converted to `R9700Mxfp4Experts` with exact exponent handling;
- synthetic model-shaped fused-QKV tensors match an independent TP4-to-TP8
  reference bit-for-bit for all eight ranks, both global KV4 and SWA KV8;
- host and device checks detect all eight writable `gfx1201` devices.

The complete checkpoint has been adopted and the TP8 service has passed direct
and LiteLLM API startup, generation, streaming, tool-loop, and image-input smoke
tests. An Anthropic `/v1/messages` request through LiteLLM correctly described a
real PNG game screenshot. Runtime profiling with vision enabled measured about
21.92 GiB of model and non-Torch allocations, a 0.86 GiB peak activation budget,
and 6.53 GiB of BF16 KV cache per GPU. Full-length quality and throughput are
not yet claimed.
